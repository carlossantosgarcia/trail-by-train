# place-search Specification

## Purpose
Search a bundled, offline index of places, gares, bus lines, GRs and curated hikes from the Tracks dock, and either fly to a point and explore a radius around it or frame an extent. Created by archiving change place-search.

## Requirements
### Requirement: Bundled offline place index

The application SHALL ship a place index generated by a reproducible build-time
script and served as a static asset, and SHALL NOT call any geocoding service at
runtime. The index SHALL cover, as distinct kinds: summits, cols, lakes and
glaciers; communes; rail stations; bus lines; curated hikes; and GR trails.

Point kinds (summit, col, lake, glacier, commune, gare) SHALL each carry a
`[lon, lat]`. Extent kinds (bus line, curated hike, GR trail) SHALL each carry a
bounding box. Records MAY additionally carry a short list of alternate names.

The index SHALL be fetched lazily — on first use of the search field, not during
application start — so it never competes with the map's first paint.

#### Scenario: No third-party request is made while searching

- **WHEN** the user types any query into the search field
- **THEN** the application MUST resolve results from the bundled index alone
- **AND** MUST NOT issue a network request to any geocoding or search service

#### Scenario: The index is a build artefact

- **WHEN** the index build script is run
- **THEN** it MUST regenerate the index from its declared sources without manual
  editing, and the result MUST be committed to the repository like the other
  generated datasets

#### Scenario: A missing optional source degrades rather than fails

- **WHEN** the index is built from a checkout where an optional source cache is
  absent
- **THEN** the script MUST emit a warning, omit that kind, and still produce a
  valid index for every other kind

### Requirement: Search field in the Tracks dock

The application SHALL provide a text field in the Tracks dock that queries the
place index as the user types. Matching SHALL be accent- and case-insensitive,
so `saint-martin` matches `Saint-Martin` and `mont aiguille` matches
`Mont Aiguille`.

Results SHALL be grouped by kind under a heading naming that kind, and SHALL be
ordered so that a prefix match outranks a word-boundary match, which outranks a
match elsewhere in the name; among equal matches, more prominent kinds and
larger communes SHALL rank higher.

On mobile the field SHALL meet the touch-target minimum. Its collapsed form SHALL be a single action within the dock's existing action row rather than a row of its own, so that search costs no additional band of chrome while unused — the map-dominance budget in `responsive-ui` leaves no room for one. Opening it SHALL move focus into the field so the keyboard appears, and SHALL be reversible without a keyboard.

#### Scenario: Accent-insensitive matching

- **WHEN** the user types `elancon` in the search field
- **THEN** a place named `Élançon` MUST appear in the results

#### Scenario: Results are grouped by kind

- **WHEN** a query matches entities of more than one kind
- **THEN** each kind MUST appear under its own heading, rather than the matches
  being interleaved in one flat list

#### Scenario: The most likely match is first

- **WHEN** the user types `grenob`
- **THEN** the commune Grenoble MUST rank above entities whose names merely
  contain the query

#### Scenario: Very short queries do not match mid-word

- **WHEN** the user has typed only two or three characters
- **THEN** results MUST be limited to records where the query begins the name or
  begins a word within it, since a two-letter fragment occurring inside a longer
  word carries no signal about what was meant

#### Scenario: Dismissing the results

- **WHEN** the user presses Escape, or clears the field, or selects a result
- **THEN** the result list MUST close

#### Scenario: Collapsed search costs no extra row on mobile

- **WHEN** the application loads on a viewport ≤ 768px and search has not been
  opened
- **THEN** search MUST be represented by one action inside the dock's existing
  action row
- **AND** the dock MUST be no taller than it is without the search feature

#### Scenario: Opening search on a phone gives it the keyboard

- **WHEN** the user taps the collapsed search action on a touch viewport
- **THEN** the field MUST appear and MUST receive focus, so the on-screen
  keyboard opens without a second tap

#### Scenario: Search can be dismissed without a keyboard

- **WHEN** the field is open on a touch viewport with nothing typed, and the
  user taps the map outside it
- **THEN** the field MUST collapse back to its action, since a touch device has
  no Escape key

### Requirement: Records are matched on their other names too

Search SHALL match a record's alternate names as well as its primary name, because the name a record is filed under is often not the name anyone uses for it. A match on an alternate name SHALL rank below any equally-good match on a primary name, so a record that is genuinely named what was typed always wins. Where the match came from an alternate name, the result row SHALL show that name, so a row whose title differs from the query reads as the right answer under its official name rather than as a mistake.

Alternate names SHALL cover, at minimum: other names recorded for a toponym; a bus line's destination text and the spoken "Ligne N" form of its number; and a GR trail's descriptive name alongside its reference.

#### Scenario: A summit found by the name people actually use

- **WHEN** the user types `barre des ecrins`
- **THEN** the summit filed as `Les Écrins` MUST be returned
- **AND** the row MUST show `Barre des Ecrins` as the name that matched

#### Scenario: A bus line found by how it is spoken

- **WHEN** the user types `ligne 62`
- **THEN** the bus line whose number is `62` MUST be returned, as it must for
  the bare query `62`

#### Scenario: A GR found by its descriptive name

- **WHEN** the user types `tour du parc national des ecrins`
- **THEN** the GR trail carrying that name MUST be returned under its reference

#### Scenario: A primary name outranks an alternate one

- **WHEN** the user types `alpe d huez`, which begins the destination text of a
  bus line and appears inside the locality name `L'Alpe-d'Huez`
- **THEN** the locality MUST rank above the bus line

### Requirement: Coverage disclaimer

The result list SHALL carry a persistent, visible note that coverage is partial, because the index is a snapshot of a handful of sources and not a gazetteer of every place in France. The note SHALL be shown both when there are results and when there are none, so an unsuccessful query is never mistaken for the place not existing.

#### Scenario: The note is visible with results

- **WHEN** a query returns at least one result
- **THEN** the result list MUST display the coverage note

#### Scenario: The note is visible with no results

- **WHEN** a query returns nothing
- **THEN** the empty state MUST display the coverage note alongside the "no
  results" message

### Requirement: Selecting a point result opens a radius around it

Selecting a result of a point kind SHALL move the map to that point and SHALL
open the Explore radius panel centred on it, naming the selected place. It SHALL
NOT immediately compute results: the user chooses a distance first.

#### Scenario: A summit seeds a radius

- **WHEN** the user selects a summit from the results
- **THEN** the map MUST move to that summit
- **AND** the radius panel MUST open, showing the summit's name as the centre

#### Scenario: A gare seeds a radius

- **WHEN** the user selects a rail station from the results
- **THEN** the radius panel MUST open centred on that station, exactly as for a
  summit

### Requirement: Selecting an extent result frames it without entering Explore

Selecting a result of an extent kind (a bus line, a curated hike, or a GR trail) SHALL frame that entity's full extent on the map and SHALL reveal it, turning on the layer that draws it if the user had it switched off. It SHALL NOT enter Explore mode and SHALL NOT open the radius panel, because a line has no centre that a circle around it would be meaningful about.

#### Scenario: A bus line is framed and revealed

- **WHEN** the user selects a bus line from the results while that provider's
  overlay is switched off
- **THEN** the map MUST frame the whole line
- **AND** the line MUST be drawn and highlighted
- **AND** Explore mode MUST NOT be entered

#### Scenario: A curated hike is framed and revealed

- **WHEN** the user selects a curated hike from the results
- **THEN** the map MUST frame the hike's bounding box, the curated overlay MUST
  be shown, and Explore mode MUST NOT be entered

#### Scenario: A GR trail is framed and revealed

- **WHEN** the user selects a GR trail from the results
- **THEN** the map MUST frame the trail's bounding box, the GR overlay MUST be
  shown with that trail highlighted, and Explore mode MUST NOT be entered
