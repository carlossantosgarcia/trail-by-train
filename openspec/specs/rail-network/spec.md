# rail-network Specification

## Purpose
The passenger rail network overlay: train lines drawn from SNCF Réseau open data, built ahead of time and streamed as vector tiles, with a visibility toggle.
## Requirements
### Requirement: Passenger rail network overlay

The application SHALL render a visual overlay of the French rail network
on top of the active basemap when the user has the rail-network overlay
enabled, so the user can see where trains run regardless of which
basemap is selected.

#### Scenario: Overlay visible on every basemap when enabled

- **WHEN** the rail-network toggle is in the "on" state AND the user
  opens the application or switches between any of the basemaps in the
  `map-viewer` switcher
- **THEN** the rail-network overlay MUST remain visible, rendered above
  the basemap raster tiles, without requiring any further user action

#### Scenario: Geometry follows real rails

- **WHEN** the overlay is rendered at any zoom level supported by the
  application
- **THEN** each line segment MUST follow the real geometry of the rail
  track within a reasonable simplification tolerance, and MUST NOT be
  drawn as a straight line between non-adjacent points

#### Scenario: Authoritative, currently-operated rail only

- **WHEN** the overlay is rendered
- **THEN** the visible lines MUST represent the currently-operated
  ("Exploitée") tronçons of the French national rail network as
  published by the SNCF Réseau "Lignes par statut" dataset, and MUST NOT
  include lines whose status is `Déclassée`, `Fermée`, `Neutralisée`,
  `Transférée en voie de service`, `Retranchée`, or any other
  non-operational status

### Requirement: Static, build-time data pipeline

The rail-network geometry SHALL be generated by a reproducible build-time
pipeline checked into the repository, and shipped as a single static
asset. The application MUST NOT require any backend, tile server, or
runtime data-processing step.

#### Scenario: Reproducible build script

- **WHEN** a developer with `curl`, `jq`, and `tippecanoe` installed runs
  the documented build script
- **THEN** the script MUST fetch the SNCF "Lignes par statut" GeoJSON
  filtered to `statut=Exploitée`, pipe it through `tippecanoe`, and
  write `public/rail.pmtiles` deterministically with no manual editing
  required

#### Scenario: Static-only runtime

- **WHEN** the application is served from a static host (no server-side
  process) and the user opens the map
- **THEN** the rail overlay MUST render correctly using only static
  assets fetched from the same origin (no external tile server, no API
  call), the bundled `pmtiles` MapLibre plugin, and the generated
  `rail.pmtiles` file

#### Scenario: Small-host friendly asset size

- **WHEN** the production build is inspected
- **THEN** the `rail.pmtiles` file SHOULD remain under approximately
  12 MB so it stays cheap to host and serve from free static hosting or
  a single-board computer. Data quality (faithful geometry, authoritative source)
  takes precedence over the size cap; small overruns are acceptable when
  justified by visible quality gains.

### Requirement: Streamed vector tiles, not load-time blob

The rail-network data SHALL be loaded by MapLibre as vector tiles
streamed by viewport, NOT as a single GeoJSON parsed in full at page
load, so the first paint stays fast on low-end devices.

#### Scenario: Tile streaming by viewport

- **WHEN** the user pans or zooms the map
- **THEN** the application MUST only fetch the PMTiles ranges needed for
  the currently visible viewport (via the `pmtiles` MapLibre protocol
  plugin), and MUST NOT fetch and parse the entire rail-network dataset
  on first load

### Requirement: SNCF Réseau attribution

The application SHALL credit SNCF Réseau whenever the rail-network
overlay is included in the rendered map, in compliance with the ODbL
licence of the source dataset.

#### Scenario: Attribution control includes SNCF Réseau credit

- **WHEN** the rail-network overlay is registered as a MapLibre source
- **THEN** MapLibre's attribution control MUST include the string
  "© SNCF Réseau" with a link to the source dataset page on
  `ressources.data.sncf.com`, in addition to the existing basemap
  attribution

### Requirement: A visual layer with a single control

The rail-network overlay SHALL remain a pure visualization layer with
no per-feature interaction. The only user-facing control attributable
to this capability is the visibility toggle.

#### Scenario: No clickable stations

- **WHEN** the user clicks, taps, or hovers on a rail line in the overlay
- **THEN** the application MUST NOT trigger any special behaviour (no
  popup, no highlight, no animation) attributable to the rail-network
  overlay

#### Scenario: Visibility toggle is the only control

- **WHEN** the application is loaded
- **THEN** the only UI control attributable to the rail-network overlay
  SHALL be the visibility toggle (per-line-type filters, restyling,
  opacity sliders, color pickers, etc. are intentionally not exposed)

### Requirement: User can toggle rail-network overlay visibility

The application SHALL expose a single UI control that lets the user
hide or show the rail-network overlay. The control's state SHALL be
persisted across reloads.

#### Scenario: Toggle control is present

- **WHEN** the user opens the application
- **THEN** a visible, labelled UI control (e.g. checkbox or switch)
  MUST be rendered that clearly indicates it controls the rail network
  overlay, and MUST reflect the current visibility state

#### Scenario: Default state is on

- **WHEN** the user opens the application for the first time (no prior
  persisted preference)
- **THEN** the toggle MUST be in the "on" position and the rail-network
  overlay MUST be rendered, preserving the prior always-on behaviour

#### Scenario: Turning the toggle off hides the overlay

- **WHEN** the user switches the toggle to "off"
- **THEN** the rail-network halo and line layers MUST be hidden from
  the map without removing the underlying source (no PMTiles re-fetch
  is required to re-enable)

#### Scenario: Turning the toggle on shows the overlay

- **WHEN** the rail-network overlay is currently hidden AND the user
  switches the toggle to "on"
- **THEN** the rail-network halo and line layers MUST become visible
  again at the same paint as before, with no visible reload of the
  basemap or other overlays

#### Scenario: Preference persists across reloads

- **WHEN** the user toggles the overlay off (or on) AND reloads the
  page
- **THEN** the application MUST restore the toggle to the most-recently
  chosen state from `localStorage`, and the overlay MUST initialise in
  that state without first flashing the opposite state

### Requirement: Rail-network toggle uses a railway-tracks pictogram

The rail-network visibility toggle ("Réseau ferroviaire") SHALL present a railway-tracks pictogram — two rails converging in perspective crossed by sleepers — as its icon, so the control reads as the *line network* and is visually distinct from the passenger-station markers (which use a front-facing "train" glyph). The pictogram SHALL be an inline SVG drawn with `currentColor` so it inherits the toggle's active and inactive colors, and SHALL NOT require any committed image asset. This requirement governs only the toggle's icon; the toggle's label, visibility behaviour, and persistence are defined by the "User can toggle rail-network overlay visibility" requirement and are unchanged.

#### Scenario: Toggle shows the tracks pictogram

- **WHEN** the user opens the application and views the Trains section
- **THEN** the "Réseau ferroviaire" toggle MUST display a railway-tracks pictogram (rails + sleepers), not a front-facing train/vehicle glyph

#### Scenario: Pictogram is distinct from station markers

- **WHEN** the rail-network overlay is visible with its passenger-station markers on the map
- **THEN** the toggle's tracks pictogram MUST be visually distinguishable from the "train" glyph used for the on-map station markers

#### Scenario: Pictogram inherits the toggle color

- **WHEN** the toggle changes between its active ("on") and inactive ("off") states
- **THEN** the tracks pictogram MUST take the toggle's corresponding color via `currentColor`, exactly as the previous icon did

### Requirement: Rail visually reads as a railway

The rail-network overlay SHALL render features with a paint that is
unambiguously recognisable as a railway at every zoom from z6 to z18,
not as a generic line. Specifically, the visible representation MUST
combine two parallel rails with perpendicular cross-tie marks placed
along the line, AND MUST render both the rails and the cross-ties in
a fixed near-black color (`#0f172a`) on top of a white halo. No user
control SHALL be exposed for changing the rail color.

#### Scenario: Twin parallel rails visible

- **WHEN** the rail-network overlay is enabled at any zoom from z6 to
  z18
- **THEN** each rail-network feature MUST be rendered with two parallel
  line layers mirrored across the underlying line geometry (one
  positive line-offset, one negative line-offset of equal magnitude)

#### Scenario: Perpendicular cross-ties visible

- **WHEN** the rail-network overlay is enabled at any zoom from z6 to
  z18
- **THEN** the application MUST render perpendicular cross-tie marks
  repeatedly along each rail-network feature, via a MapLibre `symbol`
  layer with `symbol-placement: 'line'`, so they appear perpendicular
  to the line's local tangent at every position

#### Scenario: Visual size scales with zoom without clamp artefacts

- **WHEN** the user zooms continuously from country overview (z6) to
  station detail (z18)
- **THEN** rail line widths, the gap between the two parallel rails,
  the cross-tie size, and the spacing between cross-ties MUST grow
  monotonically with zoom and MUST NOT clamp to a fixed value before
  the user reaches z18

#### Scenario: Rails and ties always render in the fixed color

- **WHEN** the rail-network overlay is enabled on any basemap
- **THEN** both parallel rail line layers AND the cross-tie marks MUST
  render in `#0f172a` over the existing white halo, regardless of any
  prior persisted user preference

### Requirement: Trains section visibility (eye) toggle

The Trains section header SHALL render an icon button (eye / eye-off) that controls the visibility of every map layer owned by the section: the rail-network halo and line layers, and the rail-stations dot and label layers. When the toggle is in the "hidden" state, all of those layers SHALL be set to `visibility: 'none'`. When it is in the "visible" state, the rail-network halo and line layers SHALL be set to `visibility: 'visible'`; rail-stations layers SHALL follow the rules in the `rail-stations` capability (which couples first-time activation of stations to this section's activation). The toggle SHALL NOT modify the persisted rail-network color (it is fixed to `#0f172a` per existing requirements) and SHALL NOT clear the user's per-layer rail-network or rail-stations preferences. The toggle's state SHALL persist across reloads in `localStorage` under the key `trainsSectionVisible`, defaulting to `false` for first-time users (matching the new default-off behaviour of `rail-stations`).

#### Scenario: Hide the Trains section

- **WHEN** the user clicks the eye button next to the Trains header while it is in the "visible" state
- **THEN** the rail-network halo and line layers AND the rail-stations dot and label layers SHALL all be set to `visibility: 'none'` in the same frame

#### Scenario: Restore the Trains section

- **WHEN** the user clicks the eye-off button while the Trains section is hidden AND the underlying rail-network per-layer toggle is "on"
- **THEN** the rail-network halo and line layers SHALL be set to `visibility: 'visible'`
- **AND** the rail-stations layers SHALL also be set to `visibility: 'visible'` (subject to the activation-coupling rules in the `rail-stations` capability)

#### Scenario: First-load default is visible

- **WHEN** a user with no persisted `trainsSectionVisible` preference opens the application
- **THEN** the Trains section visibility toggle SHALL be in the "visible" state so the per-overlay toggles (rail-network default on, rail-stations default off) take effect immediately on first paint

#### Scenario: Hidden section preserves underlying preferences

- **WHEN** the user hides the Trains section, reloads the page, then restores the section
- **THEN** the underlying rail-network toggle and rail-stations toggle SHALL retain their pre-hide values, and the layers SHALL render accordingly
